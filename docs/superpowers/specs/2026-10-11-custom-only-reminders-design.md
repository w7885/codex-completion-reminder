# Windows Codex 全自定义提醒 v0.2 设计

日期：2026-10-11。状态：用户已确认设计；实施计划待审阅。不是已完成或已安装的功能。

## 目标和已确认决策

- 修改本机正在使用的提醒器及原源码；桌面独立副本暂不修改。
- 完成、实际需要人工确认、对话选择都保留自定义浮窗渠道，用户可不用任何 Codex 原生通知。
- 每类事件互斥选择：仅自定义、仅原生、两者、关闭。仅自定义关闭同类原生，而不是两种同时弹。
- 不因自动审批产生“任务需确认”误报，不根据普通聊天提问或问号猜测。
- 允许使用 Windows 辅助功能，只读识别 Codex 实际确认/选择卡片，不记录或发送对话正文。
- 同一请求只提醒一次；手动关闭后仍在等待时不重复弹。
- 请求被处理、取消或自动撤销时，确认浮窗同步撤销。
- 继续置顶、不抢焦点；键盘或鼠标按下可关闭，输入传给原应用。

## 已验证的事实

1. Stop Hook、命令调用、命名管道和完成浮窗已经过实际回合及用户视觉确认。
2. PermissionRequest 在自动审批之前也会触发，因此它不能单独证明用户需要操作。
3. 当前安装版本的官方 App Server proxy 未能连接正在运行的桌面服务。独立启动另一个服务不等于能订阅当前桌面会话。
4. 当前版本未回答的真实选择卡片已在辅助功能树中看到：卡片容器内有单选按钮组、跳过按钮和发送按钮。已回答的历史消息不具备这组可操作控件。
5. 读取工具曾返回过时的辅助功能快照；重建读取会话后恢复。产品识别程序必须验证自己的快照刷新，不能沿用缓存当成实时状态。
6. 同版本原生配置键已从安装资源核实：[desktop] 下 notifications-turn-mode 的值域是 off/unfocused/always；notifications-permissions-enabled、notifications-questions-enabled 为布尔值。

## 组件与数据流

完成继续由 Stop Hook 发送不透明回合 ID 到托盘程序。

新增独立的只读 UIA 监测组件：定位 Codex 主窗口 → 获取新鲜的控件结构 → 判断实际待处理卡片 → 输出事件类别、不透明控件 ID、等待/已解决状态 → 托盘队列显示或撤销浮窗。

原始 PermissionRequest 只用于诊断，不直接显示确认浮窗。实际人工审批必须由已验证的可操作审批卡片触发。

不启动额外模型，不向远端发送截图或对话，不修改 Codex 应用安装文件，不代替用户批准、拒绝或回答。

## 识别与去重规则

- 选择卡片使用已验证的控件组合，不读取问题正文或选项文本来判断。
- 审批卡片需要实际控件核验。不能把自动审核状态、模型解释或历史“请确认”文字当成卡片。
- 以控件运行时标识建立当前待处理集合；同一集合元素只发送一次新增事件。
- 人工关闭弹窗只抑制该请求的再次提醒，不替用户完成请求。
- 卡片确实消失或被处理时撤销对应提醒，并释放去重状态。
- 读取失败、窗口不可访问或快照未知不等于请求已解决，不能直接清空等待集合。
- 必须覆盖前台、后台和最小化。其他聊天中尚未展示的卡片能否覆盖也必须验证，不能先宣称全局覆盖。
- 确认状态优先于完成状态，避免用户仍需操作时同时收到相互矛盾的提示；具体实现要在状态转换测试中验证。

## 原生通知互斥与设置

设置界面保留自定义渠道，不将其关闭或改成原生。只读卡片监测作为明确的可选择功能，并说明覆盖范围与兼容版本。

保存渠道时只更新三个已核实的原生通知键，其他配置、Hook 信任记录和审批策略保留。启用原生完成时使用 always，关闭时使用 off。保存前备份，失败时回滚。需要重启 Codex 重新加载外部修改的原生配置。

全局自定义提醒开关、暂停和各事件开关都必须作用到监测与展示；不擅自启用原生作为回退。

设置窗口需修正保存/取消按钮布局，并持续显示全局影响说明。

## 验证与交付门槛

先完成可丢弃的只读识别验证程序，证明它能可靠观察状态变化，再接入生产托盘程序。

- 真实选择卡片出现、回答、跳过和撤销。
- 一个真实人工审批卡片的出现与处理；测试不得静默改变用户审批策略。
- 自动审批无需人工操作时不弹确认浮窗。
- 同一请求手动关闭后不重弹；后续新请求仍提醒。
- 背景、最小化、切换聊天、多个窗口和读取失败恢复。
- 原生与自定义互斥，只有选“两者”时才双重提醒。
- 完成 Hook、输入穿透、无焦点切换等原功能回归。
- 不读取/存储问题正文，不自动点击任何确认控件。

不能通过的场景记录为明确限制，不以停止自定义、启用原生或时间延迟掩盖问题。验证失败时不安装未达标版本，并保留当前可运行版本与备份。
